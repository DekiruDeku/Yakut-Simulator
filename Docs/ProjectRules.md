# Общий свод правил работы над Yakut Simulator

Правила определяют подготовку окружения, структуру проекта, именование, разделение C++ и Blueprint, работу с ассетами, Git и проверку изменений. Они предназначены для участников разработки Yakut Simulator на Unreal Engine 5.8.

Актуальные решения и ограничения проекта закрепляются в AGENTS.md. При изменении договорённостей обновляются и этот свод, и соответствующие правила в репозитории. Последние явные указания владельца проекта имеют приоритет над историческими записями.

Редакция от 10 ноября 2026 года.

## 1. Проект и границы разработки

Yakut Simulator — VR-проект со стационарными рабочими местами. Действующая концепция включает три самостоятельные миниигры: управление парными траловыми лебёдками, сортировку и промывку рыбы, разделку рыбы ножом.

Перемещение игрока и судна выключено. Поворот камеры, трекинг головы и рук, физический захват, отпускание и использование предметов сохраняются. Код перемещения не удаляется и не включается без отдельной задачи.

Сонар, движение косяков, клиника и прежний полный промысловый цикл относятся к архивной концепции. Они не возобновляются попутно. Посторонние предметы и задания по их удалению не входят в действующие миниигры.

## 2. Окружение и сборка

Рабочая среда — Windows и OpenAI Codex. Проект находится в M:/Prototypes/Yakut-Simulator, файл проекта — YakutSimulator.uproject. Локальный движок — M:/UE/UE_5.8. Версия движка и доступные инструменты сверяются с проектом перед сборкой.

Новые рабочие каталоги создаются на диске M:; по умолчанию используется M:/Prototypes. Диск C: не используется для новых проектов и прототипов. Перед созданием проверяется абсолютный путь.

Для сборки используется установленный набор Visual Studio C++ и Windows SDK, совместимый с этим движком. Версии компилятора не меняются без необходимости. Проектные файлы решения можно пересоздавать штатными средствами Unreal Engine.

Основная конфигурация редактора — DebugGame. После изменения любого .cpp или .h редактор текущего проекта и его Live Coding Console закрываются с сохранением пользовательской работы; затем выполняется полная сборка YakutSimulatorEditor и повторный запуск. Live Coding и Hot Reload не заменяют этот порядок.

```powershell
& 'M:/UE/UE_5.8/Engine/Build/BatchFiles/Build.bat' YakutSimulatorEditor Win64 DebugGame '-Project=M:/Prototypes/Yakut-Simulator/YakutSimulator.uproject' -WaitMutex -NoHotReloadFromIDE -gather
```

Параметр -gather особенно важен после добавления новых .cpp: успешная сборка старого списка исходников не подтверждает компиляцию нового файла.

```powershell
& 'M:/UE/UE_5.8/Engine/Binaries/Win64/UnrealEditor-Win64-DebugGame.exe' 'M:/Prototypes/Yakut-Simulator/YakutSimulator.uproject' -nohmd
```

Обычное открытие .uproject использует Development-редактор и отдельную DLL проекта. Для этого способа запуска поддерживается актуальная Development-сборка.

```powershell
& 'M:/UE/UE_5.8/Engine/Build/BatchFiles/Build.bat' YakutSimulatorEditor Win64 Development '-Project=M:/Prototypes/Yakut-Simulator/YakutSimulator.uproject' -WaitMutex -NoHotReloadFromIDE -gather
```

В Editor Preferences рекомендуется включить Blueprint Break on Exceptions и Show Frame Rate and Memory. Если все .cpp компилируются, но редактор не запускается, в результате работы указываются ошибка запуска и проблемные модули; их отключение предлагается отдельно.

## 3. Структура проекта

### 3.1. Общий принцип

Верхний уровень отражает назначение системы, а нижние папки уточняют роль и тип ресурсов. Код взаимодействия, оборудование, сценарии и данные группируются так, чтобы их связи были видны из расположения файлов.

Файл помещается в наиболее конкретную папку, которая охватывает всех его потребителей. Общий ресурс поднимается к общей системе. Отдельная папка создаётся для содержательной подсистемы; одноразовые мелкие элементы не требуют собственного слоя архитектуры.

Работа ведётся в существующем runtime-модуле YakutSimulator. Новые модули и плагины выделяются при обоснованной необходимости, а не для формального разделения нескольких классов.

### 3.2. Исходники

Публичные заголовки находятся в Source/YakutSimulator/Public, реализации — в Source/YakutSimulator/Private. При появлении подпапок структура заголовков и реализаций остаётся согласованной.

В крупных подсистемах классы группируются по назначению: взаимодействие, рабочие места, оборудование, данные. Не следует складывать все компоненты разных систем в одну общую папку Components только из-за одинакового базового типа.

Общие структуры и перечисления допускается хранить в отдельных заголовках данных без исполняемой логики. Зависимости сокращаются предварительными объявлениями; определения классов подключаются там, где они действительно нужны. Заголовок .generated.h остаётся последним подключением отражаемого заголовка.

### 3.3. Контент и служебные каталоги

- Content/Base содержит общую основу взаимодействий, игровые классы, ввод и общий интерфейс.

- Content/Fishing содержит рыбу, оборудование и предметные системы. Данные, Blueprint, модели и рабочие места группируются внутри соответствующей системы.

- Content/Maps содержит действующие карты. Материалы общего назначения могут находиться в Content/Materials; материалы конкретного оборудования хранятся рядом с его системой.

- Для импортированных наборов допускается папка Packs внутри ближайшей подходящей системы. Эксперименты и удаляемые проверки явно помечаются Test.

- Scripts содержит средства авторинга и обслуживания. SourceArchive хранит неактивную реализацию вне компилируемого Source. Saved/Backups содержит резервные копии, Saved/Verification — отчёты проверок.

Правила структуры не разрешают массовый перенос существующих ассетов. Перед переносом анализируются ссылки; пути в Blueprint, конфигурации и генераторах обновляются согласованно. Бинарные пакеты изменяются только штатными средствами Unreal Engine.

## 4. Соглашение о наименованиях

### 4.1. C++

Для функций, классов, типов, параметров и переменных используется PascalCase. Имена полные и описательные, без однобуквенных переменных и произвольных сокращений. Обязательные префиксы Unreal Engine сохраняются: A для акторов, U для UObject-классов, F для структур, E для перечислений.

Название проекта известно, поэтому новые базовые классы, специфика которых определяется самим проектом, получают приставку Yakut: AYakutGameMode, UYakutGameInstance, AYakutPlayerController. Файлы называются соответственно YakutGameMode.h/.cpp, YakutGameInstance.h/.cpp и YakutPlayerController.h/.cpp.

Предметные классы именуются по ответственности: AFishingWinch, AFishSortingScenario, AKnifeItem. К каждому такому имени не добавляется приставка проекта, если она не уточняет назначение.

В существующем коде сохранены APrototypeGameMode, UPrototypeGameInstance и APrototypePlayerController. Новое соглашение задаёт именование дальнейшей разработки. Переименование существующих классов выполняется отдельным согласованным изменением с обновлением Blueprint, конфигурации и ссылок.

- В именах переменных не указываются тип и оболочка: суффиксы Ptr, Ref, Reference, Handle и аналогичные обозначения не используются.

- Для булевых переменных рекомендуется префикс b: bLocomotionEnabled, bIsHeld, bCommandConfirmed.

- Имена функций описывают действие или результат. Формулировки OnAuthority, Authoritative и аналогичные имена не используются.

### 4.2. Ассеты и варианты

В именах ассетов используются префиксы, соответствующие типу: BP для игровых Blueprint, WBP для Widget Blueprint, L для карт, SM и SK для моделей, M и MI для материалов и их экземпляров, T для текстур, DA и DT для данных, NS для Niagara System, IA и IMC для Enhanced Input.

Для BP-наследника базового класса используется согласованное имя: BP_YakutGameInstance или BP_YakutGameMode. Имя интерфейса отражает назначение: WBP_WorkstationConsole. При необходимости в дескрипторе указывается система, к которой относится ресурс.

Вариация одной сущности с дополнительной модификацией получает окончание V1, V2 и далее: BP_FishingWinchV1. Для смысловых вариантов используются их названия: BP_FishSortingConveyor_Cod и BP_FishSortingConveyor_Haddock. Окончание версии не заменяет описание назначения.

Удаляемые тестовые сущности помечаются Test с сохранением технического префикса: BP_TestFishItem, L_TestInteraction или ATestWorkItem. Полноценная игровая система не получает Test только потому, что проект находится на стадии прототипа.

## 5. Разделение C++ и Blueprint

C++ содержит общую механику, состояние и правила операций. Blueprint задаёт используемые ассеты, классы создаваемых объектов и настраиваемые параметры. Каждый действующий проектный игровой UCLASS получает BP-наследника; карты и runtime используют настроенные BP.

Нативные компоненты настраиваются в Blueprint владельца. Для самостоятельного добавления компонента доступен его BP-наследник. При смене класса компонента сохраняются параметры владельца, включая размеры зон, количество требуемых результатов и режим обработки операций.

Ссылки на проектные модели, материалы, ввод, интерфейс и карты не зашиваются в C++ по жёстким путям. Они назначаются в Blueprint, Data Asset или конфигурации соответствующей системы.

Публичная механика может сначала проектироваться в Blueprint, затем переноситься в C++, если это требуется задачей. Перенос не должен менять наблюдаемое поведение и не должен дублировать одну ответственность в двух местах.

### 5.1. Game Instance и набор карт

ScenarioMaps объявляется в C++ как UPROPERTY-массив FScenarioMapEntry в Game Instance. Запись содержит отображаемое имя и soft-ссылку на UWorld. Нативное значение по умолчанию остаётся пустым; конкретные карты задаются в Class Defaults BP-наследника.

В текущей реализации используется UPrototypeGameInstance с BP_PrototypeGameInstance. Этот BP назначается в GameInstanceClass проекта. GameMode не хранит дубликат набора карт. Виджет получает данные через Get Game Instance и приведение к проектному классу.

Существующие настройки BP не перезаписываются генератором при повторном запуске. Новые значения по умолчанию задаются при первоначальном создании либо в рамках отдельной задачи изменения конфигурации.

### 5.2. Интерфейс

Пользовательский интерфейс реализуется только в UMG Widget Blueprint. Собственные C++-наследники UUserWidget, UButton и других UI-виджетов, создание WidgetTree и вёрстка в C++ запрещены. Обработчики кнопок и привязки данных находятся в UMG.

WBP_MainMenu сохраняется самостоятельным ассетом. Контроллер, Pawn, GameMode и генераторы не создают и не показывают его автоматически. Загрузка L_MainMenu сама по себе не означает показ виджета.

Консоль рабочего места получает явную ссылку на сценарий до инициализации. Вёрстка консоли и обработка её кнопок остаются в WBP_WorkstationConsole.

## 6. Стиль C++ и Unreal Engine

- Для if, else и циклов всегда используются фигурные скобки. Однострочные if и тернарные условия не используются.

- Используется GENERATED_BODY(). GENERATED_UCLASS_BODY не применяется. Макросы UPROPERTY, UFUNCTION и аналогичные объявления располагаются на отдельных строках.

- Namespace допускается при реальной необходимости. Не следует оборачивать в него проектный код без причины.

- Для форматирования строк используется FString::Format. static_cast<void>(Value) не применяется для формального использования параметра.

- Ссылки на объекты сцены и мира в UPROPERTY объявляются через TObjectPtr или сырой указатель. TWeakObjectPtr для этих свойств не используется.

- Проверки добавляются для вероятных отказов и действительных границ системы. Уже обеспеченные предусловия не проверяются повторно без причины.

- Не создаются одноразовые вспомогательные функции и математические переменные, которые только растягивают простую формулу.

- Комментарии поясняют неочевидную бизнес-логику. Очевидный код не пересказывается; в генерируемый код комментарии не добавляются.

- В Slate используется SAssignNew. Наличие заголовков и классов виджетов проверяется в локальном UE 5.8.

- Категория свойства внутри EditInlineNew-объекта не совпадает с категорией владельца и не является её дочерней категорией.

- Действия CallInEditor при необходимости размещаются на владеющем акторе: вызов на шаблоне компонента в Blueprint Editor может не работать.

Изменение следует стилю окружающего файла. Массовое переформатирование и исправление несвязанных участков не включаются в локальную задачу.

## 7. Правила игровых систем

AVirtualRealityPawn отвечает за трекинг, ввод и общие взаимодействия рук. AWorkItem отвечает за захват, физическое отпускание, использование и события предмета. Правила обработки рыбы и работы оборудования не размещаются в Pawn.

AScenarioDirector хранит граф этапов и зависимости. Идентификаторы шагов и результатов непустые и уникальные. Подтверждённые результаты производственных действий передаются через ReportResult; нажатие Trigger само по себе не завершает профессиональную операцию.

AWorkstationScenario предоставляет состояние рабочего места, подтверждение и перезапуск. Миниигры лебёдок, сортировки и разделки сохраняют самостоятельные сценарии и оборудование.

Взаимодействия физические: учитываются коллизии, масса, скорость отпускания, шарниры закреплённых рычагов и контакт инструмента с предметом. Один предмет не удерживается двумя руками одновременно.

Разделка определяется данными вида рыбы: последовательными именованными отрезками, инструкцией и допуском. Результат зависит от траектории ножа. Потеря контакта или нарушение текущего разреза не отменяет уже завершённые разрезы.

Вода при необходимости реализуется через Water Body Ocean и Water Zone из Water Plugin. Плоскость с водным материалом не заменяет такую интеграцию и не должна становиться физической палубой.

## 8. Работа с ассетами и редактором

Перед изменением Blueprint или карты резервируется конкретный исходный пакет. Ассеты редактируются через Unreal Editor, проектные API или MCP. После изменения целевые Blueprint компилируются и сохраняются отдельно; Save All не используется ради локального исправления.

Существующие карты и заполненные параметры видов рыбы сохраняются при повторном запуске авторинга. Скрипт не должен пересобирать всю сцену для изменения отдельной модели или настройки.

Перед переносом, удалением или переименованием ассета анализируются ссылки. Нельзя редактировать пакеты, не относящиеся к задаче, или удалять пользовательские изменения ради удобства сборки.

Перед обращением к редактору проверяются фактический процесс, проект и MCP endpoint. После самостоятельного запуска первая попытка подключения выполняется через 30 секунд, дальнейшие — с интервалом 15–30 секунд как минимум до 120 секунд с момента запуска.

CVar читаются и изменяются через ConsoleVariableToolset, когда он доступен. Python remote execution после команды выключается через MCP ObjectTools, после получения её результата.

При создании unreal.Rotator в Python явно задаются pitch, yaw и roll. Пути ассетов в генераторах сверяются с их фактическим расположением; устаревший путь не является основанием создавать дубликат системы.

Исходники, Content, Config, Binaries, Intermediate, DDC, пользовательские сохранения, логи, autosaves и crash reports не удаляются в качестве попутной уборки. Архивные материалы не считаются действующим кодом или подтверждёнными проверками новой концепции.

## 9. Git и совместная работа

main содержит согласованные изменения, готовые к интеграции или передаче. Работа по задаче выполняется в отдельной ветке. Ветка dev используется как интеграционная только после её принятия командой; создавать её формально не требуется.

Для ручной разработки допускаются feature/<issue_number>_<issue_title> и fix/<short-description>. Новые ветки, создаваемые Codex, по умолчанию используют codex/<description>. Существующая рабочая ветка не переименовывается попутно.

Перед изменением проверяется состояние рабочего дерева. Пользовательские правки сохраняются. Ассеты с бинарными конфликтами не подменяются версией другой ветки без анализа; если конфликт невозможно корректно разрешить, требуется участие владельца.

Коммиты и push выполняются только по явной просьбе. Заголовки коммитов пишутся на английском и объясняют причину изменения. Перед коммитом проверяются status, diff и log, после него — итоговое состояние рабочего дерева.

Force-push, amend, обход hooks, интерактивные Git-команды и изменение git config не выполняются без соответствующего разрешения. Тексты коммитов и PR передаются через HEREDOC либо PowerShell here-string с сохранением настоящих переносов строк.

Для GitHub используется gh. Перед PR проверяются рабочее дерево, diff, tracking и история относительно базы. Описание содержит Summary и Test plan. Создание PR разрешает необходимый push; в результате возвращается URL.

Изменения бинарных ассетов координируются между участниками. В репозиторий не добавляются новые файлы более 100 МБ без отдельного решения о хранении.

## 10. Проверка и критерии завершения

Компиляция и необходимые редакторские проверки разрешены в рамках реализации. Проверяется именно изменённый путь выполнения, его зависимости и вероятные регрессии. Тесты добавляются по запросу либо когда дают содержательное покрытие.

Для текущего проекта действует запрет на запуск PIE, Automation и игровых тестовых сценариев. Такие прогоны выполняются только после нового явного указания, которое разрешает соответствующую проверку. Описание команд и режимов в документации само по себе ничего не запускает.

После изменения кода подтверждается сборка фактического editor target. После изменения BP/UMG подтверждаются их компиляция, сохранение и загрузка. Проверка реального VR-шлема, cook и packaged runtime указываются отдельно и не выводятся из успешной компиляции.

Режимы «ЦИКЛИЧЕСКАЯ ДОРАБОТКА» и «ПОЛНАЯ ПРОВЕРКА» включаются только соответствующей явной командой пользователя. Их порядок и разрешения определяются актуальным AGENTS.md. Обычная правка или переписывание документа не включает эти режимы.

В результате работы перечисляются внесённые изменения, выполненные проверки, конкретные ошибки и оставшиеся ограничения. Неполный, пропущенный или не соответствующий задаче прогон не объявляется успешным.

## 11. Диагностика и тексты

Пользовательское общение ведётся на русском, если не запрошен другой язык. Строки отладки, логов, исключений и сообщений проверок внутри кода пишутся на английском.

Основной отладочный вывод строится на UKismetSystemLibrary::PrintString. Вспомогательные файлы именуются по схеме {Entity}Debug; общий заголовок находится в Public, реализация — в Private. Для новых отладочных CVar используется YakutSimulator.Debug.{Feature}, обычно 0 — выключено, 1 — включено.

Тексты интерфейса конкретные, нейтральные и полезные для действия пользователя. Рекламные слоганы, мотивационные обещания и декоративные цепочки коротких фраз не используются.

Разработка ведётся средствами OpenAI Codex. Инструкции, SDK и конфигурация Cursor не применяются как инструкции Codex. Рабочие материалы должны открываться доступными в проекте средствами.

## 12. Поддержание правил

Принятые архитектурные решения и изменения рабочего процесса записываются в AGENTS.md одновременно с реализацией. Этот свод поддерживает общие принципы и правила команды; исторические отчёты хранятся отдельно.

Перед новой задачей сверяются текущие правила, окружающий код и настройки ассетов. Соседние проекты используются для справки; их архитектура, зависимости и ограничения не переносятся автоматически.
